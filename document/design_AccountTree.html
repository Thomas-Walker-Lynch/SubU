Purpose

AccountTree keeps light containers made of Linux accounts. A person's work is divided among accounts, each with its own files and processes, so that a web browser, an email program and a development project cannot read each other's files, without the cost of a virtual machine. This document gives the design as it is currently envisioned, for the standard numbered 5.0. It covers the accounts, the storage that keeps their data, the systems the storage is attached to, the databases, the server that changes accounts and mounts, the programs around the server, and login. Where a decision is still open it is marked as open. The features planned for later standards are listed at the end.

document/doc_2.html gives the reasoning behind the flat home directories and the idmapped views. It was written in the earlier terms described below; this document builds on it.

Ontology

Why the terms changed

The project was called SubU, for subordinate user, and spoke of a MasU, a master user, owning its SubUs. In Linux the word user is overloaded. It names the person at the keyboard, human or AI, and it names the account in /etc/passwd that the person uses, as in useradd and user name. The two are different things: one person uses many accounts, and an account has no will of its own. The design came to need the difference everywhere. Two accounts of one person are not the same account, while an account on a system and an account in a storage database can be one account in two places. With one word for both, every sentence about them was ambiguous.

The MasU and SubU terms had a second fault. Some passages spoke as though there were one MasU at the top, and others as though every SubU could be a MasU. Both were true, because master and subordinate are relative, but the terms gave no word for the top, or for an account with nothing below it.

So the word user is dropped. A person is the agent; an account is the account. The structure is described in the terms of a tree, which are relative where they should be and fixed where they should be. The project is renamed AccountTree, for what it keeps, and SubU and MasU are retired. The word user survives only in names the project does not own: uid, which is short for user id, useradd and userdel, and the kernel's user namespaces.

The account tree

Every account on a system has one parent, and root is at the top. In Linux root already administers every account, so making root the top of the tree describes what is already so, and the tree fits into Linux without changing its shape. Root keeps its one meaning.

  • person: the agent who logs in and owns data in the world, human or AI.
  • account: a Linux account, with its own uid, home, processes and sessions.
  • account tree: the accounts of a system, with root at the top.
  • parent account: the account directly above an account. child account: an account directly below one.
  • login account: an account a person logs in to, with a password or a key, at the login screen, the console or ssh. A login account is a child of root.
  • An account below a login account is a child account in the stronger sense the design uses throughout: it has no password and cannot be logged in to. It is entered from its parent, which has the server start sessions and programs in it, and its parent reaches its files through a view.
  • leaf account: an account with no child accounts.

An account's name is its parent's name, the middle dot, and its own short name: Thomas·developer·scratch is a child of Thomas·developer, which is a child of the login account Thomas, which is a child of root. In identifiers the wider category comes first, so prose says child account and parent account, and code says account_child and account_parent.

Terms

  • storage: a persistent storage device carrying accounts' data, such as the SSD inside a laptop or an encrypted USB drive. Its root is the directory it is mounted at. A storage may be moved between machines.
  • tree dir: the directory <storage root>/home/AccountTree, holding the storage database and the accounts' homes. On the disk a system runs from it is /home/AccountTree. AccountTree_admin is given a tree dir to name a storage.
  • system: an installed, running Linux, with its own /etc/passwd, its own uid numbering, and its own /home, into which the accounts kept on attached storage are mounted.
  • system account: an account in a system's /etc/passwd. storage account: an account in a storage database.
  • storage database: the SQLite database in a tree dir, describing the storage accounts kept on that storage.
  • system database: the SQLite database at /var/lib/AccountTree/system.sqlite3, a system's own record. Its system map is the authority for which storage accounts are the same accounts as system accounts.
  • database uuid: the random identifier a storage database is given when it is made. It names the database, not the storage: a copy of the database carries it too. It is not the storage uuid that a file system is given when it is formatted, which AccountTree does not use.
  • system uuid: the random identifier a system database is given when it is made, which names the system.
  • database uid: a storage account's uid in its storage database's own numbering. The account's files on the storage carry it.
  • system uid: a system account's uid, in /etc/passwd.
  • account specifier: the name of an account in one place: system <host name> <system account>, or storage <tree dir> <storage account>.
  • same account: two account specifiers that name one account in two places. The system map records which system accounts are the same accounts as which storage accounts.
  • view: an idmapped mount through which a parent account sees a child account's files as its own.
  • server: the program, running as root, that alone changes accounts, databases and mounts on behalf of persons.
  • unmanaged account: an account AccountTree does not manage, such as root, a service's account, or an account made with useradd by hand.

Accounts and names

Account names

The middle dot (U+00B7, written ·) may not appear in a short name, so a full name divides in exactly one way, and the conventional characters _, - and . remain free for use in names. It lies outside the POSIX portable character set. Making an account needs the --badname flag of useradd, and a tool that checks account names against the portable set needs its check widened. In UTF-8 the middle dot is two bytes, and an account name may currently be at most 32 bytes. That limit is set in user space, by the fixed name field of the utmp login records and by useradd, not by the kernel, which knows accounts only by uid. pkg-config prints paths holding the middle dot in a form that is not valid UTF-8; builds that pass such paths through pkg-config need the workaround given in shared/project-dependency/Python.org.

The name AccountTree is reserved, because on a running system /home/AccountTree holds AccountTree's own files. A system account made for a branch of a storage database is named with a tilde and eight hex digits, as Thomas·try~a7b3247f, described under Copies. That is a default, not a rule on names: the system map, not the name, records which system accounts belong to a branch.

Identity of an account

A storage account has an identity in its storage database, and, when the storage is attached to a running system, an extended identity on that system.

In its storage database, an account is identified by the database uuid together with its database uid. Its files on the storage are owned by that database uid, and root, mounting the storage by hand without AccountTree, sees that database uid on them. This pair is all the storage database needs to identify the account.

On a running system, the account also needs a system uid, because that numbering is the one /etc/passwd and the kernel use there. A row of the system map gives it: the row pairs the storage account's identity with a system account. The account's extended identity is its identity in its storage database, joined through the system map to the system.

Storage and systems

Storage layout

Every storage has the same layout under its root, where the root is the directory the storage is mounted at: / for the disk a system runs from, or a mount point such as /mnt/Eagle for a drive plugged in. Its tree dir is home/AccountTree under the root, so /home/AccountTree or /mnt/Eagle/home/AccountTree.

home/AccountTree/database.sqlite3 the storage database home/AccountTree/account_data/<name> the home of each storage account, by name home/<other> anything else, such as the homes of unmanaged accounts

Everything AccountTree keeps on a storage is under its tree dir, so the storage can carry other things beside it, and the storage database sits with the data it describes. account_data holds the accounts' homes; on a running system each is reached through an idmapped mount at /home/<system account>. An account named database cannot collide with the database, because the two are at different levels.

On the disk a system runs from, AccountTree's files are therefore under /home, beside the homes of unmanaged accounts. Distributions already keep /home apart from the operating system: openSUSE on btrfs makes it a subvolume outside the root snapshots, so a rollback of the root leaves it alone, and installers on other file systems commonly offer it as a partition of its own, kept when the system is reinstalled. AccountTree's files inherit this without depending on any file system. Were they on the root file system, a rollback of the root would roll back the storage database and the accounts' files with it.

A tool that walks /home sees each mounted account's files twice: at /home/<system account>, and at /home/AccountTree/account_data/<name>. A bind mount of the same file system reports the same device number, so options such as rsync -x do not stop at the mount. A backup of /home excludes one of the two.

Every storage is the same

A storage is a repository of accounts' data, whether it is built into the machine or plugged in, and a machine may have several. The SSD inside a laptop is attached at boot, before any login, in the same way a USB drive is attached when it is plugged in. Taken out of the laptop and put into a USB enclosure, the same SSD can be attached to another machine, and its accounts used there.

Copies and branches

The database uuid names the database, not the storage it is on. A copy of a tree dir, made for a backup or an archive, carries the same database uuid, and is the same database until one of the two is changed. Because a tree dir can be anywhere, an archive kept at /<storage name>/<date>/home/AccountTree can be attached by giving that tree dir.

A storage moved between systems, plugged into a desktop, then a laptop, then the desktop again, is the ordinary case. A copy used apart from its original is the case to notice: a storage restored from a backup after the first was lost, or a lost drive found again after work went on on its replacement. The record of transactions tells these apart, as git's history does:

  • Every attach and every detach is a transaction in the storage database. Two copies used apart therefore have different heads, even when no account was made or changed on either.
  • The system records every head of each storage database it sees, in its storage_head_seen table: when one of its accounts is made the same account as a system account, and at each attach and detach.

At attach, the storage's record is compared with those heads:

  • forward: its record holds the last head seen. It is the storage seen before, moved on, perhaps on another system. It attaches without comment. The system does not care how far along the storage has gone, only that it has not gone back, or sideways.
  • backwards: its head is one seen earlier, and another state of the database has been attached since. It is an older copy, or the other line of a branch.
  • sideways: its record holds an earlier head seen, but not the last one. It is a branch, two copies each changed after they parted, or an older copy whose head this system never saw.
  • unrelated: its record holds no head seen here; it parted before this system first saw it.

A storage gone backwards, sideways or unrelated is attached with a warning, and the warning and the kind are recorded. No one is kept from working: a person restoring from a backup attaches the restored storage and goes on, and its line becomes the one this system follows. Merging the two lines afterwards is done by hand in 5.0.

The two lines can also be kept apart, so that both can be attached at once and their files compared. attach <tree dir> branch makes the storage a branch: it gives the database a new database uuid, records in it the database it came from and the head they parted after, and makes a system account for each storage account that had one on the line it came from, named <system account>~<eight hex digits>. The eight digits begin the hash of the transaction that made the branch, which no other branch has, and which does not change as either line grows. The branch is then a storage database in its own right.

The same database attached twice would mount two homes at one place. When a storage's homes are already mounted from another copy of it, attach mounts nothing, and says to detach the other copy or attach this one as a branch.

Bringing two lines together again is a merge. For the storage database, a merge replays the transactions of one line onto the other where they do not conflict. For the accounts' files, it is the integration problem of 7.0, of which merging two lines of one storage is the simplest case.

These checks establish continuity, not authenticity. The hashes are not secret: they are in the storage database and the system database, and anyone who can read either can copy them into a fabricated database. Authenticity needs a secret, which is the subject of the keys planned for 6.0.

Uids are a storage database's own

The uids in a storage database are that database's own numbering. Files on the storage carry them. A storage database never adopts the uids of a system it is attached to; its accounts are mounted onto the system through idmapped mounts, which translate database uids to system uids as the files are used. A storage can therefore be moved from machine to machine without changing its files.

A storage database gives out database uids counting down from 1999999999, while systems give out system uids counting up from low numbers. A database uid is therefore not also the system uid of an account, and a file on a storage, seen without its mount, does not appear to belong to a system account it does not belong to, except in the cases given under Limits of uids. The band 1879048192 to 2147352575 is left unused by systemd's allocation of uids, so a storage database has about 120 million database uids before it leaves the band. An account brought into AccountTree from an existing one can keep its existing uid, with the keyword uid of account make; for that account the coincidence remains, behind the root-only directories of the tree dir.

A storage database never reuses a database uid. A database uid given up by a deallocated account stays retired, because files carrying it may remain on the storage, in a backup, or on another storage they were copied to.

Limits of uids

Two numberings meet on a running system: database uids, on the files of storage, and system uids, in /etc/passwd. Each has limits, set by different parties, and each limit is checked where the party that sets it is known.

The kernel. Linux uids are 32 bits. 4294967295 is (uid_t)−1 and means no uid; 65534 is the overflow uid shown for a uid that cannot be mapped; neither is given out. A database uid is never used as a system uid. At run time it meets only the idmapped mount, which accepts any uid below 4294967295, so the kernel's limit is the same on every system and a storage moved between systems is unaffected by it.

The file system. ext4, xfs and btrfs store 32-bit uids. JFFS2 and Minix store 16 bits, and FAT and exFAT store none; such storage cannot carry AccountTree accounts. This limit belongs to the storage and travels with it, so it is checked once, when the storage is made: storage make sets the owner of a test file to the first database uid, reads it back, and refuses the storage if the two differ. That check is not yet built.

The system. UID_MAX in /etc/login.defs bounds only the uids useradd picks on its own; AccountTree gives the system uid. A system's range of system uids is set by system make, 2000 to 59999 by default, and is the system's own. A storage moved to a system with a smaller range keeps its database uids, since they never become that system's uids; the smaller range limits only how many of the storage's accounts the system can make system accounts for, and is-same-account reports when the range is used up.

Where the two numberings can still meet. A database uid equals the system uid of some account when:

  • an account was brought in with the keyword uid of account make, keeping its existing uid. This is deliberate.
  • a system's own range reaches into the band. system make refuses a range that reaches 1879048192.
  • accounts from outside AccountTree have uids in the band. A directory service mapping Active Directory accounts through SSSD gives out slices of 200000 uids up to 2000200000 by default, which is inside the band, and container uid ranges in /etc/subuid can be set anywhere.
  • a storage database has given out nearly all its band, after about 120 million accounts. account make refuses below 1879048192. Should a database ever need more, a later standard chooses the next band and records it in the database, so that databases already made keep theirs.

At attach, the database uids of the storage are to be compared with the system uids in use, from the system's account database, which includes directory services, and from /etc/subuid. Each coincidence is logged with the system account that would appear to own the raw files. A coincidence is not refused: through the mounts each account sees its own files correctly, and the raw files are behind the root-only tree dir. It is reported because a tool that works by uid on the raw files, run as root, would treat them as that account's. This check is not yet built.

Tools that copy files. Backups and archives copy uids with the files. The old ustar format of tar holds uids up to 2097151, and the odc format of cpio up to 262143; database uids do not fit. GNU tar's default format, the POSIX pax format, cpio's newc format, rsync and btrfs send hold 32-bit uids, and archives of AccountTree storage use one of them.

The system

A system is a party in its own right, with its own database. Its system database, at /var/lib/AccountTree/system.sqlite3, holds its system uuid, the range of system uids AccountTree gives out, the system map, every head of each storage database it has seen, and the limits. The system owns the uid numbering of /etc/passwd: it alone decides which storage accounts get system accounts on it and with which system uids, so that record is its own and not any storage's. A storage plugged in can claim nothing; what it names in its own database grants it no system account.

A system never reuses a system uid. Its own disk keeps files carrying system uids, in /tmp, /var/spool, crontabs and logs, and a reused uid would hand them to another account. The system map therefore keeps every row it has held, retired rows included, and a system account AccountTree makes is never given a system uid that appears in it.

The system database is under /var, which holds the state programs keep, and not under /etc, which holds configuration. A system whose root file system is snapshotted, as openSUSE's is, keeps /var outside the snapshots. A rollback of the root then rolls back /etc/passwd and leaves the system map as it was: a system account made after the snapshot is lost from /etc/passwd, but its system uid stays recorded, is not given out again, and the system account can be made again from the system map. Were the system database under /etc, the rollback would also forget the system uid, and it could be given to another account while files carrying it remained under /var.

Deleting storage

AccountTree_admin storage delete <tree dir> undoes, on this system, what AccountTree did for the accounts of the storage database, then deletes the tree dir. It makes every check first, and a failed check changes nothing:

  • the storage database names no other system that has seen it, since that system's map would name a database that no longer exists, unless the keyword forget-other-systems is given;
  • no system account that is the same account as one of its accounts has a login session;
  • nothing is mounted inside the tree dir;
  • the tree dir holds only the storage database and account_data, and account_data holds only homes of the database's accounts;
  • homes that hold files are deleted only when the keyword delete-account-data is given.

For each row of this system's map naming one of its accounts, it then unmounts the home, deletes the mount point attach made, recognized as an empty directory owned by root with mode 0000, deletes the system account and its group when AccountTree made them, keeps an adopted system account, and retires the row. Last it deletes account_data, the storage database and the tree dir. Run a second time, it finds nothing to delete and says so. system delete deletes the system database, and is refused while any row of the system map is in use.

The databases

There are two kinds of database, with two schemas, schema_storage.sql and schema_system.sql. Both keep the same record of changes, described below, and are checked the same way. Each fact is kept by the party with authority over it: a storage database keeps its accounts and their database uids; the system database keeps which of those accounts are the same accounts as system accounts.

Storage database tables

  • identity: the database uuid, the uuid it was made with, from which its chain begins, and for a branch, the database it came from and the head they parted after; the series number, the head hash, and when it was made. One row. A storage database has no name for people. A name would travel with every copy of the database, and a name taken from the storage it was made on would come to mislead once the database was copied elsewhere. A database is shown by its database uuid, its series number, its head hash and the time of its last change, and log lines give the first eight digits of the database uuid.
  • standard: the AccountTree standards this database follows, one row each. Currently 5.0.
  • account: one row per storage account: database uid, name, the database uid and name of its parent, state (active, deprecated, deallocated), and times. The parent's database uid is empty when the parent is root or is carried by another database.
  • database_uid: every database uid this database has ever given out, with whether it is in use or retired.
  • system_seen: the systems that have seen this database, with when that was first and last. For the owner of the storage, and for storage delete, which will not leave a system mapping a database that no longer exists. Never authority.
  • acquaintance_database and same_account_database: other storage databases this one knows, and which of their accounts are the same accounts as accounts here, by database uid. Written into both databases. Not used in 5.0.
  • transaction_log: the record of every change, described below.

System database tables

  • identity: the system uuid, the series number, the head hash, and when the database was made. One row. The system is shown by its host name, read when it is shown, so a name for people is not kept.
  • standard: as for a storage database.
  • system_uid_range: the first and last system uid AccountTree gives a system account it makes. One row.
  • system_map: one row for each time a system account has been made the same account as a storage account: the system uid and gid, the system account's name, the database uuid and database uid, whether AccountTree made the system account or adopted one that existed, whether the row is in use or retired, and when. At most one row in use names a given system uid, and at most one names a given storage account. A row is retired, never deleted. An adopted system account may be made the same account again once its row is retired; a system uid that appears in any row is never given to a system account AccountTree makes.
  • storage_head_seen: every head of each storage database this system has seen, with the event (mapped, attached, detached), and at attach, the continuity found.
  • account_limit: the number of child accounts each system account may have below it, by system uid. A system account with no row may have none.
  • transaction_log: the record of every change.

Series number and hash chain

A transaction is one change to one database: the SQL statements a command of AccountTree_admin, or a request to the server, runs against that database, recorded together. A command can make transactions in both kinds of database; is-same-account makes one in the storage database and one in the system database.

Each transaction increments the series number, and records its statements, a description, a random number, and a hash. The hash is taken over the previous transaction's hash, the series number, the description, the statements, and the random number. The first transaction follows a hash made from the database's kind and the uuid it was made with, so no two databases' chains can coincide, and a record cannot be moved from one database into another. A branch keeps its record, and the transaction that made it a branch is in that record. The identity row holds the series number and hash of the last transaction, the head of the chain.

The chain gives order, integrity and identity of history. It does not give authenticity. Anyone holding a database can extend its chain, or rewrite it and compute new hashes. What a rewrite cannot do is keep the hashes that others have already seen: a system that remembers a head finds that the rewritten record does not hold it. Each party that remembers a head is a witness. A storage database and the system database are readable by root only, so the record is the database's own history, as a git repository's history is, rather than a log for persons to read.

The series number orders a database's history; the hash identifies it. A copy that is used goes on to make its own transactions, with the same series numbers as the original's and different contents. Their hashes differ, because the random number differs even when the same change is made to both. So two databases with the same database uuid and series number but different heads are known to have parted.

Times recorded in a database are for people to read. They are not authoritative, because clocks differ between machines. The series number is authoritative.

Standards

A program that opens a database first reads its standard table, and refuses a database that follows no standard the program follows. A database may list more than one standard, during a change from one to the next.

Fallback tools

The databases can be built by hand from SQL scripts kept in the project. They are the means of starting over if a database is lost or damaged.

  • A schema script builds an empty database where there was none.
  • Initialization scripts put in the starting data: the identity row, the standard, existing accounts, the uid range, and limits.
  • Scripts with their data written into them can write the system map rows for existing system accounts, for a system whose system database is lost.

Same accounts

A storage account's home, account_data/<name> in its tree dir, carries only its database uid. What lets it be used on a system is a row of that system's map, saying that a system account there is the same account as the storage account. The administrator states it:

AccountTree_admin is-same-account system <host name> <system account> storage <tree dir> <storage account> [make-system-account]

A keyword such as make-system-account is a word given after a command's other arguments, as the command itself is a word, not a flag. The two account specifiers may be given in either order. In 5.0 one names a system account and the other a storage account; correspondences between two storage databases come later. The host name must be this system's, which confirms that the administrator is on the machine he means. When the system account exists, it is adopted: it must be an account of a person, with a system uid at or above UID_MIN, its home must be /home/<system account>, and no other storage account may already be the same account as it. When it does not exist, the keyword make-system-account makes it, with a system uid from the system's range that no account, no group and no row of the system map has had, provided /home/<system account> is absent or empty, since the new system account would take whatever is there as its home. Without the keyword the command refuses, so that a mistyped name does not make a system account.

The first time a storage account is made the same account as a system account on a system, the storage database records that system in system_seen. That and the system map row together are what 5.0 calls an introduction; in 6.0 it is also when keys are exchanged. account make with make-system-account makes a storage account and, in the same command, a system account of the same name, the same account as it.

is-not-same-account undoes it: it unmounts the home if it is mounted from that storage, deletes the mount point attach made, deletes the system account if AccountTree made it and keeps an adopted one, and retires the row. same-account show lists which accounts are the same, with the storage accounts and the persons' system accounts that are not. same-account suggest prints is-same-account commands proposed by matching names, for the administrator to read and run; it changes nothing. Matching names is a guess, and is used nowhere else.

Someone else's storage, plugged into this system, gets nothing until the administrator makes its accounts the same accounts as system accounts here. There is no guest attach in 5.0: every storage is introduced by the administrator. A storage account named Thomas on that storage is no one here until the system map says so.

Two storage databases may say that an account of one is the same account as an account of the other, and they may say it while a system's map says otherwise. Such a claim grants nothing until a system acts on it, as in mounting a parent account's view of a child account kept on other storage. A system acts only on its own record: it does not infer that two accounts are the same from what storage databases say, and where the claims of storage databases and its own map disagree, it reports the disagreement. A child account made through the server on this system was made by this system, which records the parent relation itself.

In 5.0 storage databases and systems recognize each other by database uuid and system uuid alone. A copy of a storage database is taken for the original, and gains the system accounts mapped to the original's accounts. That is enough among one person's machines and storage. It is not enough among strangers, because either kind of uuid can be copied; keys are given under standard 6.0.

The server

What it is

The server is the one program that changes accounts, databases and mounts on behalf of persons. It runs as root, as a system service, and takes requests from any account over a Unix domain socket, /run/AccountTree/socket. The socket is open to every account; the server decides what each request may do.

The server handles one request at a time. Two requests can then never give out the same uid or the same name, and no locking is needed.

Who is asking

The server learns the requesting account from the kernel. After a client connects, the server reads the SO_PEERCRED socket option, which gives the process id, uid and gid the kernel recorded for the client when it called connect. The client does not send them, so it cannot misstate them. The server authorizes by the uid and never by the process id, because process ids are reused. The uid gives the system account's name, and that name is the prefix of any child account the account makes.

Requests

Each request is checked, carried out as a database transaction and the system changes that go with it, and answered. An account may act on itself and on any account in the tree below it, with the authority of the requesting account; this is how a child account's window, opened from its parent's, acts with the parent's authority.

  • make <short name>: make a child account of the requesting account. Checks: the short name is valid and not in use; the requesting account's limit, and the limit of every account above it in its tree, allow one more. The child account is made in the storage database of the requesting account unless another attached storage is named. Steps: a database uid, never given before, and the account row in the storage database; a system uid, never given before, and the row in the system map; the system account; the home in account_data, owned by the database uid, mode 0700; the mount of it at /home/<name>; the parent's view.
  • rename <account> <new short name>: rename a child account. The account, and every account below it, whose names begin with its name, must have no session; all are renamed together. The uids and files do not change; the homes, mount points and views are renamed with them.
  • deprecate <account>: end the account's sessions, lock it, and mark it deprecated. Its data, name and uid are kept. It still counts against the limits. A deprecated account can be restored.
  • deallocate <account>: remove a deprecated account. Its system account and views are removed, and its database uid and system uid are retired. What becomes of its data is open: the proposal is to move it to a holding directory on the storage, from which only the administrator removes it.
  • view [<account>]: report an account and its tree: names, states, storage, and whether each is mounted. Changes nothing.
  • set views: mount the requesting account's views of its child accounts that are on attached storage. Views already mounted are left as they are.
  • reconcile: compare the databases with /etc/passwd and the mount table, complete what an interrupted request left undone, make again any system account lost from /etc/passwd, and report what differs. Run at start and on demand. Administrator only.

The administrator's commands are not requests. AccountTree_admin runs as root and calls the work functions itself, so making accounts the same, attaching, detaching and setting limits work while the server is stopped, at boot for instance. The server and AccountTree_admin may both write a database; SQLite's lock lets one transaction in at a time.

Partial failure

A request makes several changes, and any of them can fail after the earlier ones succeeded. The databases record the intended state of each account. A failure leaves the intended state recorded and the system short of it; reconcile finishes the work or reports why it cannot. A request is complete only when the system matches the databases.

Protocol

A request is one JSON object on one line, carrying the protocol version, the request name, and its arguments. The answer is one JSON object on one line, carrying whether the request succeeded, its result, and on failure a message for a person to read.

The service unit

The server's systemd unit must not set PrivateMounts, ProtectHome or any other option that gives the service a mount namespace of its own. A mount made inside such a namespace exists only for the service, and no account ever sees it.

Limits

Making a child account takes a database uid from a storage database, and a system uid and a system account from the system, and the system's are finite. Without a limit, one account could take all of them. Each system account has a limit on the number of accounts in its tree below it, counting accounts at every depth and counting deprecated ones. Limits are kept in the system database. The administrator sets them with AccountTree_admin limit set. A system account with no limit set has a limit of 0, and cannot make child accounts.

A child account made by a child account counts against the limits of every account above it. The starting value suggested for a login account is 100.

Mounts

Idmapped mounts

Every AccountTree mount is an idmapped mount: a bind mount that carries a translation of uids, applied by the kernel to every permission check and to every file made through it. Idmapped mounts need Linux 5.12 or later, and a file system that supports them, such as ext4, btrfs or xfs. An idmapped mount is kernel state, with no process behind it, so it survives the restart of the server and the end of any session. A mount through FUSE, such as bindfs, does neither.

AccountTree makes the mount with the kernel's own calls, not by running mount. open_tree clones the source as a mount not yet attached anywhere; mount_setattr gives it nosuid, nodev and the idmap; move_mount places it. The kernel is given the idmap as a user namespace: a child process is made in a new user namespace, its uid and gid maps are written, and the namespace is handed to mount_setattr. A map line reads <id inside> <id outside> <count>; for an idmapped mount the kernel takes the uid on disk, the database uid, as the id inside, and the id outside, the system uid, as the uid seen through the mount.

Attaching storage

AccountTree_admin attach <tree dir> verifies the storage database's standards and hash chain, compares its record with the heads seen here, as described under Copies and branches, then reads this system's map for the rows naming that database uuid, and nothing else. For each, it checks that the storage account is active and that the system account exists with its system uid and with its home at /home/<system account>, and mounts the storage account's home there, translating the database uid to the system uid. Storage accounts with no row are logged as skipped. The mounts are nosuid and nodev, since a storage can carry set-user-id programs and device files. Files on the storage owned by database uids the mount does not translate appear owned by nobody.

Views

A parent account sees each of its child accounts at ~/account_child/<short name>: an idmapped mount of the child account's home that translates the child's uid to the parent's. Files there appear to be the parent's, and files the parent makes there belong to the child. The directory is named for the property each of its entries has, being a child account, so the name is singular. Views are set when storage is attached, for the parent accounts already in session, and at each session's start, through set views. Views are designed in outline only, and come next after this document's other parts are built.

Mount points

A mount point must exist before a mount, so /home/<system account> exists for every known account, attached or not. While nothing is mounted on it, it is an empty directory owned by root with mode 0000, and marked immutable. No account can enter it, and nothing can be written into it to be hidden later by the mount.

Login and entering

A login account whose storage is not attached has no home. A login into the empty mount point finds no initialization files, and does not read them later when the storage arrives. Login is therefore refused for a managed login account whose home is not mounted.

The check is in PAM, which every way of logging in passes through: the display manager, the console, ssh, su and machinectl shell.

account sufficient pam_succeed_if.so uid = 0 quiet account required pam_exec.so quiet /usr/local/lib/AccountTree/home_present

home_present allows the login when the account is not managed by AccountTree, or when /home/<name> is a mount point, and refuses it otherwise. The first line keeps root able to log in whatever the check does.

A child account is not logged in to. It is entered from its parent: the parent asks the server to start a session or a program in it, and the server does so only for an account below the requester in the tree. Whether a child account may ever be logged in to directly is open.

A session, when it starts, sends set views. The server knows the account from the socket, so a session can set only its own views.

Programs and modules

  • AccountTree: the person's program. Its commands send requests to the server; its window command opens the resource window, which shows the account's child accounts and their states and sends the same requests. Runs as the person's account.
  • AccountTree_admin: the administrator's program. Root. Its commands: system make, system show and system delete; storage make, storage show and storage delete, each given a tree dir; account make; is-same-account, is-not-same-account, same-account show and same-account suggest; attach and detach; and limit set. At boot, before logins are allowed, attach is run for every storage present, the disk inside the machine included, so that /home is populated. Detaching is refused while a system account it would unmount has a session. Unlocking an encrypted storage and mounting it come later.
  • AccountTree_server: the server, started by its systemd unit. Nobody types it.
  • home_present: the PAM check.
  • The schema and initialization scripts.

Each program keeps the RT convention of a command line interface apart from its work functions, and the modules are imported as libraries: a window, a server or a test calls the functions directly, never the command line. There are two layers of work functions. Those that change the system run as root; AccountTree_admin and the server import them. The person's functions send requests to the server and return its replies; AccountTree and the window import them. The socket between the layers is where privilege changes.

The modules are named and shaped as they are meant to stay. Where a direct call is not yet written, a wrapper function stands in its place, named for what it does here and commented with the direct call it will become:

  • kernel: direct calls, made through ctypes. The idmapped mount through open_tree, mount_setattr and move_mount; unmounting through umount2; the mount table from /proc/self/mountinfo; the immutable flag through the FS_IOC_SETFLAGS ioctl; login sessions through sd_get_uids in libsystemd.
  • system_account: reading system accounts directly, through the C library, and changing them through wrappers, system_account_make, system_account_delete and system_group_delete, which run the shadow suite's commands for now. In the future each will be a direct call: the lines of /etc/passwd, /etc/shadow, /etc/group and /etc/gshadow edited under the C library's lock, lckpwdf, each new file written beside the old one and renamed into place.
  • database, system, storage and same_account: the databases and the work functions on them.
  • account_tree, authority, resource_kind and window: the person's side.

Keeping the root functions separate, and their calls direct, lets them later be moved into a smaller program of their own, or into the kernel, where an account tree with root at its top fits Linux as it is.

Open questions

  • What deallocation does with an account's data.
  • Whether a child account may ever be logged in to directly.
  • Whether a parent account's views are removed when its last session ends, or left until the storage is detached.
  • How resources other than accounts and storage, such as network zones and devices, are recorded in the database.

Road map

Standard 5.0 is the design above. Later standards add the following, each described in its own section. A database lists the standards it follows in its standard table, so a database moves to a later standard by listing it, and a program that follows only an earlier one refuses it.

  • 6.0: longer account names; keys, for unlocking storage and recognizing it; signed heads; deduplication; deep freeze.
  • 7.0: integration of archives and of child copies, and merging of lines; a property file system.
  • Later, version not yet assigned: guests.

Guests. A person who plugs storage into someone else's machine and works there, with no administrator introducing it first, makes the machine a display with a processor for whatever storage is brought to it. The guest's storage accounts would be given system accounts at attach, in a band of system uids of their own, recorded in the system map as transient, and deleted at detach, with no rights to anything of the machine's owners. In 5.0 every storage is introduced by the administrator. Guests wait until keys, automatic attach, and the protection of a machine from what a stranger's storage carries, are understood.

Standard 6.0

Longer account names

Account names built from a chain of parent names grow long, and 32 bytes, with two for each middle dot, is soon reached. 6.0 is to allow names of 128 bytes. The limit is in user space: the login records and useradd. Distributions are replacing the utmp records with wtmpdb and lastlog2, which have no fixed name field; openSUSE has done so. What remains is the check in useradd, which goes away when AccountTree edits the account files itself. Whether a system already accepts longer names is found by making a test account with a name past 32 bytes.

Keys

In 5.0, databases and systems recognize each other by database uuid and system uuid. 6.0 adds two uses of keys.

Unlocking storage. A storage's file system is encrypted with LUKS2, which keeps up to 32 key slots, any of which opens it. Each person whose accounts are on the storage has a slot, opened by a passphrase or by a hardware token such as a FIDO2 key. When a storage is introduced to a system, the administrator opens it once, and the system adds a slot of its own, with a key it keeps, so that the storage is opened and attached on that system without asking anyone for a password. systemd-cryptenroll already enrolls such slots, and can seal a key in the machine's TPM, the security chip on its motherboard, so that the key is useless away from that machine. A slot can be removed from any machine that can open the storage, which is how a stolen laptop is cut off from it. Opening a storage with a key the system enrolled is also the proof that it is the storage that was introduced, which uuids and hashes cannot give: a fabricated storage cannot be opened with that key. The keys a system keeps make the place they are kept a target in the way /etc/shadow is; sealing them in the TPM is the protection. The disk inside the machine can be treated the same way, its /home opened by the system's own slot at boot, which keeps every storage alike.

Signed heads. Each database and each system also holds a key pair. Each transaction's hash, which covers every transaction before it, is signed with the private key of the party that wrote it, so that a head can be shown to have been written by whoever holds that key, and not only to follow from the heads before it. The signature is checked with the public key, and the first is-same-account between a system and a storage database records each one's public key in the other's database, alongside its database uuid or system uuid. On attach, each side checks that the other holds the private key matching the public key recorded for it, so a copied database uuid or system uuid alone is refused. A storage is not a running party, so a database's private key is a file on its storage, and a full copy of the database copies the key too; protecting the key, for example inside the storage's encryption, is part of the 6.0 design.

The migration touches only the identity and acquaintance tables and the programs that read them. A 6.0 database adds the key columns and lists both 5.0 and 6.0 in its standard table while keys are exchanged. The system map, uids and the account table are unchanged, because an account is still identified by its database and its database uid.

Deduplication

A storage gathers copies of the same files, from old archives and from copies made between accounts. On btrfs, two files with the same content can be made to share their extents, after which the content is stored once while the files stay separate: a later write to one of them is written apart from the other. The kernel call that does this, FIDEDUPERANGE, compares the two ranges byte for byte before sharing them, so a false match on a hash cannot corrupt data. Tools such as duperemove and bees find candidates by hashing and leave the comparison to that call.

The AccountTree server already runs as a service, and is a natural home for a background pass over attached storage. The pass keeps an index of content hashes, gives the kernel call the pairs whose hashes match, and so keeps each storage compacted as it is used. On a file system without shared extents, the pass reports duplicates and changes nothing. The same index serves integration in 7.0.

Deep freeze

A person's accounts, archives included, may not fit on one portable storage: 500 GB, say, against more data than that. Most of it is seldom read. Deep freeze divides an account's home into a working part and a frozen part by access time. Files not read for a long time move to the frozen part, which is kept on other storage, and a copy to a storage that cannot hold all of it takes the working part only. Whether the frozen part's directory tree stays visible, with its content brought in when its storage is attached, is open.

Access times are recorded only when a file system is mounted with atime or relatime. relatime, the Linux default, updates a file's access time at most once a day, which is enough here; under noatime nothing is recorded, and deep freeze cannot work. Bringing a working part back after it was changed elsewhere is the integration problem of 7.0.

Standard 7.0

Integration

Two kinds of integration are needed. The first brings the files of old archives into the current accounts. The old archives have older, less mature directory structures, and the aim is to place their files in the current structure, not to keep the old structures. The content-hash index kept for deduplication shows which old files already exist in the current tree, under any name, and leaves the rest to be placed.

The second brings back a child copy: part of an account's home copied to a portable storage, changed there, and returned. Its changes are merged into the original. A change to the directory structure on either side is the hard case, as when a file is moved on one side and changed on the other. Two lines of one storage, described under Copies and branches, are merged the same way.

Property file system

Both kinds of integration are hard because a file has one place in one tree. A file system organized by properties, or tags, would let a file belong to an old structure and a new one at once, and make a directory a query. AccountTree's contract with storage is that an account's home is a directory mounted at /home/<system account>, and the mounting is one function in the code. A home provided by a property file system changes that function and nothing else, provided the file system supports idmapped mounts or translates uids itself. At that point the AccountTree project is expected to fork.
