Introduction

A Subu is an isolated user environment operating within a broader parent system. It functions as a strict User Container. Each subu possesses its own namespace, isolated processes, and dedicated I/O resources.

The core architectural goal of the subu system is administration without elevation. A Master User has the ability to completely administer a subordinate user environment without requiring sudo privileges or system-wide root access. The master user accomplishes this through a dedicated suite of tools and a specialized file system architecture.

Design Decisions and Architecture

Namespacing

Subu accounts require a naming convention that links them logically to their master user while remaining fully compliant with legacy Linux utilities. The system utilizes the underscore (_) as the namespace separator, or appends a sequential integer or hash.

Example account names are Thomas_developer and Thomas_incommon.

Historically, the architecture explored using the middle dot as a separator. However, strict POSIX compliance and legacy toolchains, such as Emacs TRAMP regular expressions, fundamentally reject non-ASCII characters in hostnames and usernames. Adopting the underscore ensures absolute compatibility across the entire Linux ecosystem without requiring complex workarounds. To manage path length and organizational clarity, the system relies on an SQLite database to map these system-level names to human-readable subu aliases.

The File System Dilemma

Attempting to nest subu home directories within the master user's home directory (e.g., /home/Thomas/subu/developer) creates an intractable conflict with POSIX permissions and Access Control Lists (ACLs).

If a subu is nested, the operating system requires group execute permissions on the master's home directory to allow traversal. If a person attempts to restrict this using ACL masks, the subu retains sovereign control over its own files. A subu executing a standard chmod 600 on a file recalculates the ACL mask to zero, instantly severing the master user's access to that file and causing subsequent system backups to fail with permission errors.

The Dual Layer Architecture

To resolve the file system dilemma, the subu architecture utilizes a dual layer approach, splitting the physical data location from the administrative view.

The Physical Layer

Every subu home directory resides directly under /home, entirely flat and parallel to the master user account.

/home/Thomas /home/Thomas_developer

Placing the directories side by side eliminates traversal conflicts. The subu relies purely on standard POSIX ownership of its dedicated path, ensuring absolute sovereign control over its workspace and preventing permission changes from breaking the directory structure.

The Management Layer

To grant the master user administrative access without violating the physical layer permissions, the system utilizes ID-mapped mounts.

A system service establishes a mount point within the master user's workspace, pointing to the subu's physical directory:

/home/Thomas/subu/developer -> /home/Thomas_developer

The kernel translates the subu's user ID to the master user's user ID in real-time. Through this mount, the master user perceives absolute ownership of all subu files. If the subu locks down a file in the physical layer, the master user retains the ability to read, modify, or repair it through the management layer.

Hardware Access and the Virtualization Horizon

Currently, because subu accounts utilize logind to acquire their own session seats, they inherit strict hardware isolation rules. Modern Linux dynamically assigns hardware ACLs (such as audio and primary graphics nodes) to the active seated user.

The system currently accepts a "first to grab" behavior for these resources. The first subu session to initialize and claim the audio socket or the primary display node holds the exclusive lock for the duration of its session.

The long term architectural goal is to eliminate this bottleneck by virtualizing the graphics card and distributing it among multiple users, thereby maintaining strict isolation without requiring exclusive locks.

Fundamentally, hardware virtualization and user process or memory virtualization are identical solutions. The historical separation between a virtual machine and a user namespace represents an incomplete modernization of the operating system user model. The subu architecture views these concepts as a unified system. Future iterations will seek to integrate an existing Linux GPU virtualization layer directly into the user container, granting each subu parallel, isolated access to the underlying hardware substrate.

System Setup and Initialization

The architecture depends on a dedicated setup account to bootstrap the environment during system boot.

If a subu or master user creates an ID-mapped mount directly during their session, the Linux login daemon (systemd-logind) will aggressively terminate the background FUSE processes upon logout, destroying the management layer.

The system setup process executes independently of user sessions. It queries a central SQLite database to determine the registered subu relationships, constructs the /home/master/subu directory structures, and establishes the ID-mapped mounts. Crucially, the setup process assigns ownership of these mounts to the master account. Because the mounts are created by a boot-level service, they persist indefinitely, surviving all individual user logouts.

User Manual

Locating Files and Directories

Data locations depend on the perspective of the user interacting with the system.

For the Subu

  • Home Directory: /home/Thomas_developer
  • Perspective: The subu operates in a standard Linux environment. Files are owned by the subu. All paths behave normally.

For the Master User

  • Primary Workspace: /home/Thomas
  • Subu Management Directory: /home/Thomas/subu/developer
  • Perspective: The master user navigates into the subu directory to administer subordinate accounts. All files within this directory appear to be owned by the master user. Modifying a file here instantly modifies the physical file for the subu.

Backups

When a person initiates a backup of their home directory, they must instruct the archiving tool (such as tar or rsync) to respect filesystem boundaries. Passing the --one-file-system flag prevents the backup utility from traversing into the /home/Thomas/subu mounts, avoiding infinite recursion loops and duplicate data capture. The physical subu directories are backed up via separate, independent archive routines.
